## 二、逐项复盘：为什么发生、怎么解决、如何避免

### UI-01：外部任务启动后，UI 没有同步到制作页

**现象与原因**

蓝牙启动豆腐后，设备已经打印 `TouFu Make Start` 和当前任务状态，但屏幕仍停留在首页。启动命令、任务调度、页面同步和 LCD 刷新是不同环节，任务启动日志不能单独证明页面已显示。

旧实现依赖 `!tofu_flow_requested` 这一一次性接管条件。标志置位后，如果页面回到首页或任务在其他页面结束，旧标志可能残留，阻止后续恢复制作页。原有测试每轮调用 `UiFlowConfigure()` 清空状态，只覆盖首次启动，漏掉了连续使用场景。

**已经怎么解决**

1. 在 `lvUIshowTask()` 中统一调用 `refresh_external_flow_page()`，由 UI 任务读取实际流程状态，蓝牙接收回调无需直接操作 LVGL。
2. 豆腐运行时，若当前不在制作页、停止确认页或停止等待页，恢复到豆腐制作页。
3. 保留停止确认和停止等待页，避免周期同步覆盖用户操作；任务切换或在非运行页结束时清除旧接管标志。
4. 植物奶、豆浆和清洗通过各自桥接接口跟随运行任务；接管页面不再发送一次启动命令。
5. 增加 `UIFlow` 日志和 `test_external_tofu_reentry()`，覆盖不重新初始化控制器的连续任务与页面恢复。

**以后如何避免**

- 页面同步以实际任务状态为依据；“已提交命令”“已观察到运行”“正在停止”分别记录。
- 测试必须包括连续运行两次、跨页面结束、切换任务后再进入、停止确认页保留和不重复启动。
- 排查按“收到命令 → 当前任务 → UIFlow 页面变化 → 屏幕实际显示”逐段取证。
- 豆腐的重入修复不能自动推定植物奶、清洗具备相同恢复能力，新增场景时分别检查各自的接管条件。

**定位与证据**：[myLvgl.c](../components/myLvgl/myLvgl.c)、[plantmilk_ui_flow.c](../components/myLvgl/plantmilk_ui_flow.c)、[clean_ui_flow.c](../components/myLvgl/clean_ui_flow.c)、[UI 回归用例](../tests/test_plantmilk_ui.c)。提交 `b4787f4`（10-30）；详细证据见[专项排查记录](蓝牙启动豆腐UI未同步与烧录编码问题排查记录.md)。其中明确记载主机回归通过，但尚无新固件实机跳转成功记录，不能直接标为实机问题已关闭。

### UI-02：模拟 UI 与正式运行模式混淆

**原因**：`MYLVGL_UI_VALIDATION_MODE=1` 会模拟传感器与流程，不从 UI 下发真实硬件命令，正式外部任务同步逻辑也不执行。电脑上修改源码后，设备中的旧固件不会自动改变。

**已经怎么解决**：豆腐、植物奶、清洗共用 [myLvgl.h](../components/myLvgl/include/myLvgl.h) 的同一个开关；当前默认 `0`，并在初始化时输出 `UIFlow: validation=0, external_sync=1`。主机测试支持明确指定模式 `0` 或 `1`。

**以后如何避免**：每次联调先看设备启动日志确认模式，再检查页面和硬件行为；两种模式分别回归。发布前还需核对独立的 `MYLVGL_ASSUME_PRESS_CHANNEL_PRESENT`：当前为 `1`，压制通道默认通过；需要真实通道检测时，应在硬件输入接通后改为 `0`，使用 `PressPartsCheckSetChannelPresent()` 提供状态。凝固剂低液位也仍有预留输入，不能把所有检查项都视为已接通真实硬件。

**验证边界**：专项排查开始时工作区模式已经是 `0`，不能继续把模拟模式认定为那一次首页未跳转的已确认根因。

### UI-03：禁用按钮仍获得焦点，或检查页错误使用旧传感器状态

**现象与原因**

只把 Start/Continue 画成禁用样式，不能阻止旋钮或程序直接选中它；点击处理时刷新传感器，还可能改变焦点，导致用户原本按下的 Back 被错误解释。另一方面，原始在位输入为低电平有效；初始零值、过期缓存或逐项读取的不一致状态，也可能被误认为“全部在位”。

**已经怎么解决**

1. `sensor_checked_selection()` 在进入页面和选择控件时统一约束：检查未通过只能聚焦 Back。
2. 豆腐机器检查、压制部件检查、植物奶机器检查、漂洗准备和深度清洁准备五类页面采用同一原则。
3. 从通过变为未通过时回到 Back；恢复后保留 Back，由用户重新选择 Start/Continue。
4. 相关短按处理先保存用户选择，再刷新传感器，避免刷新改变本次点击含义；实际启动仍检查是否满足条件。
5. `DataCenterGetSensorSnapshot()` 原子读取站 2 输入，未收到有效数据或数据年龄达到 1000 ms 时返回无效；UI 使用“快照有效且对应位为 0”判断在位，不等待一次新的串口事务。

**以后如何避免**：同时维护视觉状态、焦点可达性和动作执行条件。新增检查项必须测试首次无数据、低电平极性、恰好超时、任一传感器缺失、恢复后选择，以及按 Back 时状态突变；禁止直接把未验证缓存值当成检查通过。

**定位与证据**：[ui.c](../function/UI/ui.c)、[SensorSnapshot.h](../task/DataCenter/SensorSnapshot.h)、[DataCenter.c](../task/DataCenter/DataCenter.c)、[传感器快照测试](../tests/test_sensor_snapshot.c)。提交 `8aff374`、`14c6516`；UI 用例包含 `test_sensor_snapshot_validity()` 和 `test_sensor_focus_lock()`。本次未重新运行这些测试。

### UI-04：旋钮方向、步数、页面端点与编辑操作不一致

**现象与原因**

机械编码器的 A/B 边沿不等于一个完整机械步；采集层与 UI 层若重复缩放，会出现转多格才动一次。统一对所有页面取模，会让普通按钮从末尾绕回开头；双按钮简单“取反”则会出现同方向旋转仍来回切换。编辑态与浏览态混用，也会让旋钮同时改变数值和焦点。

**已经怎么解决**

- 编码器用 A/B 状态转换表累计四分之一步，完成一个有效机械步才修改 `encCounter`；相邻抖动抵消，两位同时跳变丢弃未完成步。
- 有效计数在中断中直接更新，UI 读取累计净变化；按键消抖与长按判定放在任务中。诊断日志原先在计数之后入队，后续已按 UI-12 移除该日志链路。
- `UI_ENCODER_PULSES_PER_SWITCH` 从 `3` 调整为 `1`，当前每个有效机械步切换一项；物理方向由 `MY_ENCODER_FORWARD_DIRECTION` 统一校准。
- 首页、硬度和配方等圆盘选择页循环，并将 Back 纳入循环；普通参数和流程按钮页在首尾停止。
- 双按钮页按方向选择目标端点，同向继续旋转保持端点；进入编辑态只改变当前参数，退出后才移动焦点。

**以后如何避免**：在编码器层定义计数单位，在 UI 层定义导航规则，禁止各页自行反转物理方向。新增页面先确定是否循环、Back 是否可达、编辑时是否移动焦点，并测试快速转到端点后立即反转、短按与长按、日志队列拥塞。

**定位与证据**：[MyEncoder.c](../components/MyEncoder/MyEncoder.c)、[MyEncoder.h](../components/MyEncoder/include/MyEncoder.h)、[myLvgl.c](../components/myLvgl/myLvgl.c)、[编码器测试](../tests/test_encoder_interrupts.py)。提交 `8aff374`、`14c6516`；`test_encoder_navigation()` 覆盖导航、端点与反转行为。

### UI-05：时间数字跳动、凝固剂文字和编辑箭头错位

**原因**：比例字体中各数字宽度不同，时间更新后重新居中会改变分钟与冒号位置；凝固剂名称长度不同，旋转 90 度后视觉横向位置还受原坐标轴和字形尺寸影响。只给某个字符串写死偏移，容易在另一种值或另一种编辑状态下失效。

**已经怎么解决**

1. 新增 [ui_font_tabular_22.c](../function/UI/Font/ui_font_tabular_22.c)，复用原 Manrope 位图，让 `0～9` 使用统一进位宽度，时间字段关闭字符对间距。
2. 时间专用字体只用于对应字段，其他普通文字保持原字体。
3. 凝固剂编辑复用独立箭头，固定箭头位置；根据编辑状态、名称及字形尺寸对齐文字，柠檬酸编辑态在箭头间居中。
4. 植物奶容量显示补上 `ml`，避免只有数字而缺少单位。

**以后如何避免**：时间、计数等位置敏感字段采用等宽数字；布局同时检查最短和最长文字、浏览/选中/编辑三种状态及旋转后的边界。动态文字与初始文字应共用数据来源，避免只修改初始化文本却被后续刷新覆盖。

**定位与证据**：提交 `14c6516`（10-31）；[ui_firm_tofu.c](../function/UI/Tofu/ui_firm_tofu.c)、[ui_more_options.c](../function/UI/Tofu/ui_more_options.c)。`test_blending_time_stability()` 包含 `00:30～03:00` 的边界及 `01:00 → 01:15` 时分钟和冒号像素不变的检查。本次未重新执行。

### UI-06：UI 图片造成内存/存储空间不够，使用 LZ4 压缩解决

**遇到了什么问题**

随着 UI 页面、背景图和高亮图增加，原始图片直接编译进固件，图片资源占用过大，出现了“内存不够、图片资源放不下”的空间问题。因此采用 LZ4 压缩图片，降低固件体积，为现有页面及后续资源留出容量。这是采用 LZ4 的直接目的，应作为独立问题记录。

这里需要分别核算三类空间，才能判断解决是否有效：

| 空间 | 存放内容与不足原因 | 本次处理方式 |
| --- | --- | --- |
| Flash / OTA 应用分区 | 固件代码与静态图片数组；原始图片体积大，挤占应用容量 | 图片离线压缩，只让实际引用的压缩数组进入最终固件 |
| PSRAM 运行内存 | 显示时使用的已解压图片；同页多张大图或旧缓存不释放会增加峰值 | 按图片需要解压并缓存，换页/换图释放旧缓存 |
| 内部 RAM / DMA 内存 | 任务、LVGL 对象与显示传输缓冲区 | 图片解压缓冲显式分配到 PSRAM；复用页面对象，显示缓冲保留分配失败回退 |

**为什么会出现**

- SquareLine 导出的图片是像素数组。在 RGB565 加 Alpha 的当前格式下，一张图约需 `宽 × 高 × 3` 字节；例如 `182 × 448` 就需要 244,608 字节，普通图、高亮图和背景图会继续叠加。
- 图片编辑文件或 `.c` 文件的表面大小不能代替最终链接后的占用，必须检查 BIN、链接映射和应用分区余量。
- 只生成压缩文件却继续引用原始描述符，不会获得预期节省；所有图片提前解压或缓存长期不释放，也会增加运行内存压力。

**已经怎么解决、具体怎么做**

1. 电脑端使用 [ui_lz4_pack.py](../tools/ui_lz4_pack.py) 对原始像素执行 **LZ4 HC -9** 离线压缩，核对像素长度，并解压逐字节比较。
2. 生成带 `LZ4I` 标志、`_lz4` 后缀的图片描述符，通过 [ui_lz4_assets.h](../function/UI/ui_lz4_assets.h) 的声明和别名接入各页面配置。原始源文件保留用于重新打包，未被引用的原始数组由链接器移除。
3. 设备端只编译普通 LZ4 解压器，注册 [ui_lz4_decoder.c](../function/UI/ui_lz4_decoder.c)，调用 `LZ4_decompress_safe()` 解码；校验解压长度，分配或解码失败时返回失败。
4. 解压缓冲使用 `MALLOC_CAP_SPIRAM | MALLOC_CAP_8BIT` 分配，避免大图片像素缓冲占用内部 RAM。LZ4 压缩降低的是存储占用，显示时仍需要完整像素空间，例如上述图片解压后仍需 244,608 字节 PSRAM。
5. 配合 UI-07 的图片缓存及换页/换图释放，兼顾重复解压带来的卡顿和运行内存占用；保持单个 `ui_Screen`，复用图片/文字槽位。

**解决效果与依据**

以下数据来自 [LZ4 专项记录](UI图片LZ4压缩实施与问题处理记录.md)，均为当时构建快照：

| 验证对象或阶段 | 记录结果 | 说明 |

| 单张 `182 × 448` 图片 | 原始 244,608 字节，压缩大小 1,147 字节 | 大面积重复像素的个例，不能外推到全部图片 |

### UI-07：图片压缩后，界面刷新反而明显变慢

**原因**：当时 `LV_IMG_CACHE_DEF_SIZE=0` 关闭了解码缓存。屏幕分块刷新会多次打开同一张图，反复申请 PSRAM、解压、绘制和释放，压缩节省 Flash 的同时增加了每帧工作量。

**已经怎么解决**：将 `CONFIG_LV_IMG_CACHE_DEF_SIZE` 设为 `16`，并同步 `main/lv_conf.h`；跨逻辑页面时释放上一页缓存，同页动态更换图片源时释放旧源缓存。同页后续刷新可复用已解压图像。

**以后如何避免**：缓存的 `16` 是解码会话数量，不是 16 KB，必须按原始像素大小估算内存；当前构建启用 `CONFIG_LV_CONF_SKIP=y`，应确认 `sdkconfig` 生效，不能只修改 `main/lv_conf.h`。回归时连续切换多页与高亮图，观察 PSRAM 是否持续下降、是否存在反复解压和首次进页的额外耗时。

**定位与证据**：[ui_lz4_decoder.c](../function/UI/ui_lz4_decoder.c)、[ui.c](../function/UI/ui.c)、[LZ4 专项记录](UI图片LZ4压缩实施与问题处理记录.md)。专项记录记载缓存开启后刷新基本恢复，但全量逐页实机检查与 PSRAM 峰值测量仍需补充。

### UI-08：把目标 FPS 当成实测刷新速度，或只靠提高帧率解决卡顿

**原因**：目标周期、实际完整帧数和旋钮动作到画面完成的延迟是不同指标。静态页面可能没有脏区域，即使目标是 10 FPS，实际完成帧数也可以为 0。

**已经怎么解决**

- 当前默认目标 10 FPS，可配置范围为 1～20 FPS；UI 使用 `ceil(1000 / FPS)` 设置显示刷新周期，10 FPS 为 100 ms，20 FPS 为 50 ms。
- 显示驱动从渲染开始计时，到最后一块 DMA 完成时记录完整帧；同一帧分块传输不会重复计数。
- 当前驱动优先使用两个 60 行内部 DMA 缓冲区，分配失败先释放已有分配，再尝试 40 行，最终回退到静态 10 行缓冲区。

**以后如何避免**：先定位重复解压、重复全屏重绘、传输耗时和调度等待，再调整目标 FPS。缓存图像放 PSRAM，DMA 缓冲按驱动能力使用内部 DMA RAM；增加缓冲区时核对内部内存余量。完整交互延迟还需在编码器事件产生时打点，与对应画面最后一次 DMA 完成关联，现有帧耗时不能替代这项测量。

**定位**：[lv_port_disp.c](../components/myLvgl/lv_port_disp.c)、[显示统计测试](../tests/test_display_diagnostics.py)、[显示诊断字段说明](../README.md)。当前已具备诊断实现，不据此宣称实机已稳定达到 20 FPS。

### UI-10：UI 源码已经修改，设备仍表现为旧版本

**原因与证据**

**后续执行顺序**：重新配置与构建 → 烧录参数预检 → 实际烧录 → 同次 ELF 监视 → 页面实机回归。具体命令见[专项排查记录](蓝牙启动豆腐UI未同步与烧录编码问题排查记录.md)和[构建烧录说明](../script/README.md)。

### UI-11：上电花屏与首帧亮屏等待时间优化

记录日期：2026-11-03。涉及 ESP32-S3、ST7796、320 × 480 的 16 位 I80 显示接口，背光由 GPIO48 控制，高电平点亮。

**现象与原因**

用户反馈第一次上电时出现约 1 秒的彩色噪点，随后恢复正常页面；采用首帧完成后再点亮背光的处理后，又反馈亮屏等待约两秒，需要进一步缩短。

代码中确认存在提前亮背光的路径：`ScreenInit()` 后马上调用 `ScreenSetBrightness(100)`，随后才初始化 LVGL、加载首页和创建 UI 任务。此时 LCD 显存尚未写入完整有效画面，背光已经打开，随机显存就可能形成可见花屏。原来背光 GPIO 也要到屏幕初始化时才配置，前面的外设初始化期间没有由应用主动保持关闭。

亮屏时间还包含初始化和调度等待，并非两秒都用于传输像素：Wi-Fi 原先在屏幕之前初始化，工程在面板复位和初始化后各叠加了 100 ms，而 ST7796 驱动内部已有相应等待；普通首次刷新还要等 UI 任务启动及帧率定时器。

**已经怎么解决**

1. `app_main()` 的第一项操作调用 `ScreenBacklightHoldOff()`：GPIO48 先写低，再配置输出和下拉，在 NVS、蓝牙等初始化前关闭背光。
2. PWM 初始占空比保持 0。`ScreenSetBrightness()` 在首帧就绪前只保存目标亮度，即使请求 100%，实际背光也保持关闭。
3. 在 LCD 的 `on_color_trans_done` 回调中判断当前是否为本帧最后一块；只有最后一块实际传完，才在临界区内设置 `first_frame_complete`。
4. UI 任务通过 `lv_port_disp_service_backlight()` 调用 `ScreenNotifyFirstFrameReady()`，应用保存的亮度。LEDC 更新放在任务上下文，中断仅发布状态；门控只释放一次，目标亮度为 0 时仍保持关闭。
5. 为缩短等待，删除工程层两个额外的 100 ms，保留驱动内部的复位和退出睡眠等待；提前创建唯一的 UI 任务，先显示首页，再初始化 Wi-Fi、蜂鸣器及其他业务任务。
6. 首帧在 UI 任务的 8 KiB PSRAM 栈上调用 `lv_refr_now()` 立即刷新。首页显示后，UI 等待应用就绪通知；业务任务创建完毕后才进入正常交互，避免访问尚未就绪的资源。

**如何判断最后一块已经传完**

LVGL 按脏区域和绘图缓冲大小拆分刷新，内部只有在 `last_area` 和 `last_part` 同时成立时，才标记 `flushing_last`。`lv_disp_flush_is_last()` 读取该标志；在 DMA 完成回调中读取，就同时满足了“本帧最后一块”和“这一块实际传完”两个条件。

```text
上电关闭背光
→ 初始化面板、LVGL 和首页
→ UI 任务立即渲染并逐块传输
→ 最后一块 DMA 完成，且 lv_disp_flush_is_last() 为真
→ 设置 first_frame_complete
→ UI 任务释放背光门控，显示完整首页
→ 应用初始化其余功能并通知 UI 启用交互
```

必须在 `lv_disp_flush_ready()` 前读取最后一块标志，因为该函数会清除刷新状态。默认 60 行缓冲时全屏为 8 块，但代码不写死块数，也不靠是否到达屏幕底部判断；缓冲回退或局部刷新后仍由 LVGL 标志判断。

主程序等待首帧的 `UI_FIRST_FRAME_WAIT_MS=1500` 是异常上限，完成即继续，不会固定等待 1.5 秒。超时也不会绕过 DMA 完成条件提前点亮背光。

**效果与验证边界**

- 首帧门控回归通过：覆盖提前关闭 GPIO、最后一块提交后仍保持关闭、最终 DMA 完成、ISR 不调用 LEDC、亮度保存、重复服务和传输失败路径。
- 启动握手和正常模式真实 LVGL/UI 回归通过；优化版固件构建、分区容量检查及烧录参数预检通过。
- 代码层已移除 200 ms 的重复固定等待，且将 Wi-Fi 初始化移出首帧显示路径；尚无优化版的完整冷启动测量结果，不能宣称整机已缩短到某个具体秒数。
- 新增 `DisplayBoot` 的 `LCD ready`、`UI ready` 和 `First frame ready` 阶段日志，时间从应用入口附近计算，不包含 ROM、bootloader 和此前系统启动阶段。

**以后如何避免**

- 始终将“背光可以点亮”的条件绑定到首帧实际传输完成，不用固定延时猜测，也不在提交 DMA 后立即释放像素缓冲。
- 优化亮屏速度时先分段测量初始化、渲染及传输耗时；保留驱动要求的面板时序，只删除已确认重复的等待。
- 复杂首帧绘制继续使用 UI 任务栈；首页提前显示时，交互仍等业务初始化完成，保持单任务管理 LVGL。
- 实机验收覆盖完全断电再上电、复位、后续切页和亮度调整，留存运行版本、画面及阶段日志。
- 若进入应用前仍亮屏，结合原理图和上电波形检查背光使能的硬件默认电平；应用代码尚未执行的时间段需由电路保证背光关闭。

**定位与验证入口**：[main.c](../main/main.c)、[RGB.c](../components/RGB/RGB.c)、[lv_port_disp.c](../components/myLvgl/lv_port_disp.c)、[myLvgl.c](../components/myLvgl/myLvgl.c)、[首帧回归测试](../tests/test_display_startup.py)。

### UI-12：开启旋钮日志后上电重启，以及变量、打印和队列方案的限制

**现象、配置变化与证据边界**

- 用户反馈：将 `KNOB_ENCODER_LOG_ENABLE` 开启后设备反复重启，并明确确认“上电还没转旋钮就重启”。
- 最初排查时，日志队列容量为 `ENCODER_LOG_QUEUE_LENGTH=128`；关闭日志时回调为 `NULL`，不创建该队列。
- 本次记录时再次读取工作区：`main.c` 中日志开关已为 `1`，`MyEncoder.c` 中队列容量已为 `16`。这些是记录前已有的本地代码改动，不是本次文档操作的修复结果。
- 尚未收到重启前的异常文本、Backtrace、实际内部堆余量或最大连续空闲块数据。因此不能把“内存不足”“任务栈溢出”或“看门狗”写成已确认根因，也不能认定缩小到 16 条后已恢复正常。

**为什么未转旋钮也可能重启**

移除前，开关不只是控制 `ESP_LOGI()` 是否输出，还控制 `encoder_debug_config.log_callback` 是否为非空。旧 `enctest()` 启动时，在 GPIO 中断初始化之前执行：

```c
if (log_callback) {
    log_queue = xQueueCreate(ENCODER_LOG_QUEUE_LENGTH,
                            sizeof(my_encoder_event_t));
    ESP_ERROR_CHECK(log_queue ? ESP_OK : ESP_ERR_NO_MEM);
}
```

如果申请失败，队列返回 `NULL`，随后 `ESP_ERROR_CHECK()` 触发 `abort()`。当前启用 `CONFIG_ESP_SYSTEM_PANIC_PRINT_REBOOT=y`，异常后自动重启，下一次启动又走到相同位置，便可能形成重启循环。这条路径无需旋钮动作，也无需执行第一次 `EncoderDebugPrint()`。

此外，队列申请成功后也会减少内部余量，后面的 `gpio_install_isr_service()` 等初始化仍可能申请失败；必须以串口报错表达式和 Backtrace 区分。确认队列失败时应能看到类似以下信息，下面只是识别样例，不是已采集的设备输出：

```text
ESP_ERROR_CHECK failed: ... 0x101 (ESP_ERR_NO_MEM)
function: enctest
expression: log_queue ? ESP_OK : ESP_ERR_NO_MEM
```

**为什么是 128 条，容量究竟占多少内存**

128 是原代码手动设定的待处理日志容量，不是硬件要求、一次旋转的事件数量，也不是全生命周期最多允许 128 次旋转。每完成一个有效机械步才生成一条旋转日志事件，不是每个 A/B 边沿都生成一条。

旧 `my_encoder_event_t` 在该目标上包含 8 字节时间戳、4 字节累计计数和 4 字节方向，共 16 字节。时间戳用于判断相邻旋转是否间隔超过 200 ms，方向用于识别反转，计数是该步发生时的快照。日志里的手势次数不等于转满一圈。

| 容量 | 事件存储空间，不含队列管理和分配开销 |
| --- | --- |
| 8 条 | 128 字节 |
| 16 条 | 256 字节 |
| 32 条 | 512 字节 |
| 128 条 | 2048 字节 |

`xQueueCreate()` 在创建时就预留完整容量，空队列也占这些空间。原 128 条容量可以容忍较多打印积压，但源码中没有基于最大旋转速度、打印耗时和任务调度计算出“必须为 128”的依据；容量应按实际日志需求和内存预算确定。

队列满时，`xQueueSendFromISR()` 立即返回失败；当前代码忽略返回值，因此丢弃本次新日志，保留已有待打印记录。任务取走记录、腾出空间后，后续事件可以继续入队。计数在入队前已经更新，所以丢日志不会丢掉累计计数；UI 仍读取计数的净变化。日志可能从某个累计值跳到较后的值，队列满本身不会调用 `abort()`，与创建时申请失败是两种情况。

**为什么“512 KB SRAM + 2 MB PSRAM”仍不能保证申请成功**

即使按用户所述的硬件容量计算，也不能把两者相加后当成队列可用内存。512 KB 是内部 SRAM 总容量，内部代码、静态数据、任务栈、Wi-Fi/蓝牙资源、显示 DMA 缓冲等会占用其中一部分；并非所有内部区域都能作为普通可按字节访问的空闲堆。2 MB PSRAM 是另一类内存，也要以启动识别结果和运行时统计确认实际可用量。

本机 SDK 的分配路径为：

```text
xQueueCreate()
→ xQueueGenericCreate()
→ pvPortMalloc()
→ heap_caps_malloc(size, MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT)
```

- `MALLOC_CAP_INTERNAL`：必须是内部内存，且不能因 Flash/PSRAM 缓存关闭而变得不可访问。
- `MALLOC_CAP_8BIT`：必须支持按字节访问；不是“8 位 CPU”或“只能存 8 位数”。
- `|` 将能力标志组合起来，分配结果必须同时满足两项，不是任选其一。PSRAM 支持字节访问，但不满足 `INTERNAL`。
- 普通 `malloc()` 在当前 `CONFIG_SPIRAM_USE_MALLOC=y` 下可以按配置选择内部或外部内存；这不会覆盖 FreeRTOS 显式要求内部内存的规则。
- `CONFIG_SPIRAM_MALLOC_RESERVE_INTERNAL=32768` 是保护显式内部内存申请的配置，不应把它简单解释成额外消耗或永久不可用的 32 KiB；相关申请仍需看对应能力的实际余量。

动态队列需要在同一次分配中容纳管理结构和全部事件存储区。空闲总量足够，最大连续块也可能不足。例如，内部仅剩 1200、1500、1800 字节三个空闲块，总共 4500 字节，仍无法分配一个超过 2048 字节的块。这是假设示例，不是本次设备实测结果；不同区域的空闲量也不能任意拼接。

现有 `.map` 只能说明相应构建的静态布局，不能直接得到设备运行到 `enctest()` 时的内部空闲堆。显示成功采用 60 行双缓冲时，另需 `320 × 60 × 2 字节 × 2 = 76800 字节`，即 75 KiB 内部 DMA 内存；实际采用哪种缓冲回退方案仍需看设备日志。判断队列能否申请，应关注同一时刻、同一能力条件下的内部 `free`、`largest`，不能用 PSRAM 余量或总 RAM 容量代替。

**用户提出的方案：哪些能用，哪些不能直接替换**

这些方案并非全部不能使用。应先确定需要“最新累计值”还是“尽量完整的逐步事件”，再看是否由中断访问，以及内存分配是否仍可能失败。

| 方案 | 可以解决什么 | 限制及当前结论 |
| --- | --- | --- |
| 任务直接读取 `encCounter` 并打印，不建队列 | 观察当前值、两次采样间的净变化，减少缓存开销 | 可以使用，UI 本来就在这样读取计数；不能保证记录采样间发生的每一步、反转及停顿时间 |
| 每走一步，直接在中断里打印变量 | 及时观察该步数值，无需任务事后读取历史 | 常规 `ESP_LOGI()` 不适合当前 ISR；即便使用受限场景接口，打印耗时仍可能干扰边沿采集 |
| 给计数变量加 `volatile` | 避免编译器省略相应访问或复用旧的寄存器值 | 当前变量已经有 `volatile`；不能保留历史、立即调度任务，也不提供互斥或通用原子性 |
| 中断通知任务，再由任务读变量 | 让任务尽快处理，减少轮询 | 可以使用，但通知不是每步数据的快照；多次变化仍可能先于一次读取发生 |
| 把 `ESP_LOGI()` 换成 `ESP_DRAM_LOGI()` 或 `esp_rom_printf()` | 在满足代码、字符串和数据可访问条件时，进行少量受限上下文输出 | 可以用于短、低频的诊断；不能消除串口等待，且仅更换回调内打印函数不会取消原队列申请 |
| 把队列从 128 条缩小到 16 条等 | 降低事件存储及连续块要求 | 可以使用；需要接受更早丢日志，不能保证其他内部申请成功，也不能据此证明重启已解决 |
| 使用 `xQueueCreateStatic()` | 使用提前准备的控制块和存储区，创建时无需动态申请堆 | 可以使用，当前 SDK/配置支持；同等容量仍占同等事件空间，可能减少其他资源的可用内存 |
| 使用 `xQueueCreateWithCaps()` 指定 PSRAM | 显式选择动态队列的内存能力 | SDK 支持，但不能在保持当前 IRAM ISR 访问方式不变的前提下直接把队列整体搬到 PSRAM |

**为什么读取变量、逐步打印和 `volatile` 不能互相替代**

若中断和打印任务恰好交替运行，读取变量确实可以依次打印 0、1、0；问题在于任务调度不保证这种顺序：

```text
T0：变量初始为 0
T1：中断完成一步 +1，写入 1
T2：中断完成一步 -1，写回 0
T3：打印任务才获得运行机会，读取到 0
```

这里的 `+1/-1` 只是计数示例，不代表当前安装的旋钮物理方向校准；本工程物理正转计数为 -1。

`volatile` 不会阻止 T2 覆盖 T1，也不会在变量里自动保存旧值；即使 T3 按要求访问变量，也只能得到当时的 0。先连续五步再读取，可以得到净变化五步，但无法仅凭最后一个值还原各步的时间和中间方向。任务通知也不能保证任务赶在下一步前读取；即使记录通知次数，也没有自动记录每一步的方向及时间。

如果只需要当前计数，直接读取变量是合理的简化方案；不应为了查看当前值强行保留逐步日志队列。如果需要回放每一步，则需在发生时保存必要事件，队列、带同步规则的环形缓冲等都可作为实现方式。有限队列本身也不保证绝不丢事件，必须说明满时策略。

**为什么不能把打印函数简单换掉，就认为中断没有影响**

`ESP_LOGI()` 涉及格式化、常规日志锁及输出路径，不应直接移进当前 GPIO ISR。`ESP_DRAM_LOGI()` 可用于中断/缓存受限场景，格式字符串由宏放到 DRAM，标签可用 `DRAM_STR("ENC")`；若用 `%s`，被引用字符串也必须在相关时段可访问。`esp_rom_printf()` 是更底层的 ROM 输出，当前 SDK 声明说明不支持浮点和 `long long` 格式，不能不检查格式就照搬现有回调。

这些接口仍需占用处理时间及串口资源，不保证多上下文日志完整不交错。当前串口为 115200 波特率，按常见 8N1 计算，20 字符在线路上传输约需 `20 × 10 / 115200 ≈ 1.74 ms`。FIFO 有空间时函数可能较快返回，满时可能等待；1.74 ms 是传输预算示例，不是每次 ISR 的固定耗时。高速或长文本输出可能使后续 A/B 边沿无法逐个处理，因此仅适合少量诊断，不应逐边沿长期打印，也不应为打印延长临界区。

如果打印仍在 `EncoderDebugPrint()` 回调里，单纯替换 `ESP_LOGI()` 不会改变 `enctest()` 创建队列的逻辑，因而不能消除队列申请失败路径。反过来，直接中断输出是一种整体路径调整，需要重新检查采集时序，不能当作只替换函数名。

**为什么不能把当前日志队列直接放进 2 MB PSRAM**

当前 ISR 使用 `IRAM_ATTR`，并通过 `gpio_install_isr_service(ESP_INTR_FLAG_IRAM | ESP_INTR_FLAG_LEVEL1)` 注册。ISR 内的 `xQueueSendFromISR()` 会立即访问队列控制块并复制事件数据，不是只保存指针、等任务运行后才触碰队列。

该配置要求中断在 Flash 缓存关闭期间仍可工作。当前未开启 PSRAM 指令/只读数据搬移等相关选项，外部 PSRAM 在某些缓存关闭期间不可访问。若使用 `xQueueCreateWithCaps(..., MALLOC_CAP_SPIRAM | MALLOC_CAP_8BIT)`，本机 SDK 会将队列控制块和事件存储区都按该能力分配；在缓存关闭时触发中断，就可能因访问 PSRAM 而产生缓存访问异常。

`IRAM_ATTR` 只约束函数所在位置，不会把它引用的队列、字符串或其他数据自动搬入内部 RAM。仅将控制块留在内部、事件区放在外部也不能直接解决，因为 ISR 入队仍要写事件区。`xQueueCreateStatic()` 的缓冲区同样受访问条件约束，不会因为采用静态创建就自动变得安全。

这不是 PSRAM 完全不能用于日志。只在合适的普通任务上下文访问的日志存储可以考虑 PSRAM；若中断需在缓存关闭期间继续采集，可先写小型内部缓冲，再由任务转存外部 RAM。这样会增加搬运和同步环节，需要根据日志量决定是否值得。另行修改中断类型或缓存配置属于整体设计调整，会改变采集及时性和运行条件，不能在本次排查中当成无影响的单行替换。

工程已将图片解压缓冲明确分配到 PSRAM，UI 任务栈也显式使用 PSRAM；并非没有利用外部内存。不同对象按访问条件选择位置，不能按哪个区域剩余更多直接互换。

**静态队列的作用和不能解决的部分**

`xQueueCreateStatic()` 由应用提供长期有效的 `StaticQueue_t` 控制块及 `长度 × 单条大小` 的存储区。若使用内部静态数组，可在编译/链接时确定这笔内部占用，避免创建阶段受动态堆碎片影响；不得使用函数返回后失效的普通局部数组作为缓冲。

128 条静态队列的事件区仍是 2048 字节，16 条是 256 字节。减小容量和改为静态分配是两项不同措施，不能把容量减少带来的节省归功于“换函数”。静态预留还会减少后续堆余量，可能使其他初始化申请失败；它不增加 SRAM 总容量。`xQueueCreateWithCaps()` 则仍是动态申请，失败时仍可能返回 `NULL`，且其释放应使用配套的 `vQueueDeleteWithCaps()`。

**后续处理原则与验收，不代表已经实施**

1. 先核对设备固件与源码版本，保存首次异常完整输出和同次 ELF 的 Backtrace 解码结果；以失败表达式确认是否为日志队列、GPIO 服务或其他资源。
2. 若确认是分配问题，关注队列创建前的 `MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT` 空闲总量及最大连续空闲块，并与 PSRAM 分开统计；不能用启动较早或重启后的余量代替失败瞬间数据。工程已有 `PrintHeapUsage()` 可报告 `free/largest/min_free`，但运行日志开关及其时序需另外核对，事后统计不能保证捕获初始化失败瞬间。
3. 根据需求选方案：只看累计值可用任务采样；需要逐步记录才评估小型内部队列、静态存储或其他事件缓存。可选调试功能申请失败时，应考虑降级关闭日志，而不是阻止旋钮和整机工作；该容错当前仍需另外实现和验证。
4. 分别验证日志关闭、开启但未旋转、慢转、快转、连续反转、按键及日志积压。确认丢日志不会改变累计计数，且不把读取净变化误认为完整逐步轨迹。
5. 若调整 ISR 打印或任何外部内存访问，额外核对缓存关闭场景及串口拥塞下的中断耗时；使用 PSRAM 的决定必须同时检查代码、数据和所有调用路径。

### UI-13：切换 Custom Milk 时旋转图层分配失败，空指针清零引发重启

**现象与直接原因**

在植物奶配方选择页切换到 Custom Milk，ESP32 整机重启。用户提供的异常为 `StoreProhibited`，异常地址 `0x00000000`，调用链为 `lvUIshowTask → LVGL 刷新 → lv_draw_sw_layer_create → lv_memset_00`，本次清零长度为 14,592 字节。

软件绘制的不可分片图层分支先调用 `lv_mem_alloc()`，随后直接清零，最后才检查返回值是否为 NULL。分配失败时，判空还没执行就已写入空地址。Custom Milk 包含较宽的双行标题，文字旋转 90° 需要额外的完整图层缓冲；主机真实渲染测到的最大单图层也是 14,592 字节。未在实机失败瞬间直接采样最大连续空闲块，不能进一步把碎片程度认定为已测得结论。

**实际内存配置的易错点**

固件设置了 `CONFIG_LV_CONF_SKIP=y`，LVGL 使用 `sdkconfig`，而不是 `main/lv_conf.h` 中的数值。故障构建实际为 `CONFIG_LV_MEM_SIZE_KILOBYTES=32`；只修改后者显示的 64 KiB 不会扩大设备中的池。该池虽位于 PSRAM，仍是独立、有容量上限的 TLSF 池，不能把 ESP32 剩余 PSRAM 总量直接当成 LVGL 可分配量。

**已经怎么解决**

1. 在 `lv_draw_sw_layer_create()` 中将 NULL 检查移到清零之前；分配失败直接返回，由上层已有路径跳过本次图层绘制，不修改绘制上下文。
2. 将实际生效的 `CONFIG_LV_MEM_SIZE_KILOBYTES` 从 32 改为 128，保留外部 BSS/PSRAM 放置方式。最终链接映射确认 `lv_mem.c.obj` 的池位于 `.ext_ram.bss`，大小 `0x20000`（128 KiB）。实际 Kconfig 原已启用透明图层支持。
3. 主机 UI 测试原先使用系统 `malloc`，没有覆盖设备固定池不足。现从固件 `sdkconfig` 导入 LVGL 选项，使用同源、同容量的 TLSF 池，并检查正常渲染时每次图层创建均成功。
4. 保留标题内容、字号及旋转方式，未通过缩短 Custom Milk 文字规避故障。

**历史验证与边界（2026-11-06）**

- 真实 LVGL/TLSF 中人为占用内存，让上下文仍可分配但像素缓冲无法分配；分别测试透明和不透明图层各 50 次，共 100 次失败。均安全返回，空闲量、最大连续块和绘制上下文不变，内存完整性检查通过；释放占用后重新创建图层，逐字节确认清零并验证销毁后的恢复。
- 连续切换配方 200 次，共创建 2,880 个图层，全部正常分配；最大单图层 14,592 字节。主机记录峰值 116,610 字节，结束时最大连续空闲块 112,592 字节，不能将这些主机数值当成 ESP32 实测峰值。
- `nv_build` 构建通过，经 COM12 烧录、哈希校验和复位后，用户实机反复切换并停在 Custom Milk；SHL-500W 抓取到正常页面。同步采集的 55 秒串口记录中，心跳连续递增，未发现崩溃或重启标记。
- 本次短时实机回归未复现原故障；长期连续切页、实际峰值及碎片变化仍需专项采样。

**以后如何避免**

- 所有分配操作先检查返回值，再清零、复制或更新上下文；扩池同时保留失败路径的容错。
- 核对实际编译配置、生成的 `sdkconfig.h` 和链接映射，确认池的大小及所在内存区域；区分固定池空闲量、最大连续块和系统 PSRAM 总余量。
- 旋转文字回归覆盖最宽、最长、双行文本及连续切换；主机使用固件同源配置，并主动测试分配失败后的无泄漏、上下文保持和恢复绘制。

## 四、以后修改 UI 的固定检查流程

### 1. 开始前确认版本与边界

- 记录分支、提交号、样机和预期运行模式；区分源码、构建产物与设备固件。
- 明确本次修改属于页面显示、导航、传感器门控、任务桥接或显示驱动，找准对应文件。
- 先查看 `git status --short`，保留已有本地改动；历史记录与代码不一致时写明差异。

### 2. 实现时保持一致规则

- 页面配置、普通图、高亮图和动态文字使用同一套状态来源，避免初始化后被另一份数据覆盖。
- 进入页、旋钮选中、传感器刷新和实际点击共用门控规则；参数浏览与编辑明确区分。
- 页面显示由 UI 任务管理，业务任务通过状态和接口交互；收到命令后继续确认任务是否真正运行。
- 新增图片检查压缩映射和缓存释放；新增字体检查字符集、压缩支持及实际构建入口。
- 单 screen 架构下复用对象，不在每次页面切换时重新创建 screen、图片或文字对象。

### 3. 回归验证覆盖连续使用

主机具备 GCC 和项目所需 LVGL 源码时，可执行已有测试；以下为后续复查命令，本次未执行：

```powershell
python tests/test_plantmilk_ui.py --ui-validation-mode 0
python tests/test_plantmilk_ui.py --ui-validation-mode 1
python tests/test_encoder_interrupts.py
python tests/test_display_diagnostics.py
python tests/test_display_startup.py
```

找不到 GCC 时，UI 和编码器脚本可用 `--cc` 指定主机 GCC 路径。UI 主机测试产物和截图位于 `build/ccache/plantmilk-host/`；模拟 RTOS、传感器和任务状态的主机测试不能替代真实串口、双核调度及 LCD DMA 验证。

| 必查场景 | 通过标准 |
| --- | --- |
| 正常模式与模拟模式 | 行为符合模式定义；模拟模式不下发硬件命令 |
| 每类页面的正反旋转 | 方向一致，循环/端点规则正确，Back 始终可达 |
| 检查页任一条件失败 | Start/Continue 不可聚焦、不执行；Back 可用 |
| 无数据、超时、恢复与点击瞬间变化 | 不因旧值或焦点刷新误启动 |
| 时间及不同长度参数文字 | 最短/最长值、选中/编辑状态下位置稳定，无箭头重叠 |
| 蓝牙、串口、旋钮启动 | 能跟随实际任务，页面接管不重复创建任务 |
| 停止确认、停止中、自然完成 | 页面不会被周期同步覆盖，结果与停止状态正确 |
| 连续两次制作及任务切换 | 不依赖重新初始化 UI，无残留接管状态 |
| 结果页进入清洗 | 先进入清洗准备页；明确选择 Start 且检查通过后才启动 |
| 连续切页和动态换图 | 图片正确、缓存可释放，内存不随操作持续下降 |
| 旋转文字与图层内存不足 | 覆盖最宽/双行标题及连续切换；使用实际固定池配置；分配失败不崩溃、不泄漏、不破坏上下文，释放内存后可恢复绘制，详见 UI-13 |
| 新增或批量替换图片资源 | 压缩校验通过，链接未误带原始大数组，固件满足 OTA 容量限制，实测 PSRAM 峰值与内部 RAM 余量满足运行需求 |
| 冷启动、复位与首帧显示 | DMA 未完成前背光关闭，完整首帧写入后再点亮；亮度和后续页面正常，亮屏耗时有版本及测量记录 |
| 旋钮采集与诊断功能变更 | 当前验证无日志情况下的冷启动、旋转、短按和长按；未来恢复日志时另行验证容量、溢出策略及内部 free/largest，可选日志不应阻止整机启动 |

按 [script/README.md](../script/README.md) 完成构建和烧录预检，实际烧录后核对设备版本，再执行上表中的实机项目。记录“主机测试通过”“构建通过”“预检通过”“实机通过”各自的证据，不能互相替代。

```powershell
git status --short
git diff --check
git diff --cached --name-only
```

暂存区不得包含 `build/`、`ccache/`、`.ccache/`、`.cache/`、`__pycache__/`、`.venv/` 或其他构建产物。若发现缓存已被跟踪，应仅从索引移除并保留本地文件，按项目规范处理。

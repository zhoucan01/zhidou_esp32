# BLE 发送无响应分析结果

## 结论

本次无响应发生在 Windows 上位机与 ESP32-S3 之间的 BLE GATT 传输层，
不是 Modbus 地址、功能码或 CRC 错误。

进一步交叉检查确认，重新连接后“写入成功但无回复”的首要根因是 ESP32
没有记录控制特征 `AutoIoSeverHandle` 的 Notify/Indicate 订阅状态。因此生成的
控制响应会在 `SendMessage()` 中被静默丢弃，NimBLE 发送 API 根本不会被调用。

首轮请求返回的 `AccessDenied` 则是上位机侧独立存在的写入失败。MTU、分片、
重复订阅和长响应发送问题仍然存在，但不是解释第二阶段完全无回复所必需的条件。

## 固件直接根因：控制特征订阅状态遗漏

控制响应最终通过以下链路发送：

```text
BluetoothSendControlResponse()
  -> SendMessage(..., AutoIoSeverHandle)
```

但 `Bluetooch.c` 中以下四个订阅状态函数只处理温度、压力、时间和系统监控
特征，没有处理控制特征：

- `indication_is_enabled()`
- `notification_is_enabled()`
- `set_indication_enabled()`
- `set_notification_enabled()`

因此，即使 Windows 已成功为控制特征写入 CCCD，ESP32 收到
`BLE_GAP_EVENT_SUBSCRIBE` 后也不会保存该句柄的订阅状态。发送响应时：

```c
bool use_indication = indication_is_enabled(channel);
bool use_notification = notification_is_enabled(channel);
```

两个结果始终为 `false`，随后命中：

```c
(!use_indication && !use_notification)
```

并直接返回。该缺陷可以确定造成控制响应在发送前被丢弃，与重新连接后
“Windows 写入成功、固定等待超时、没有 Notify”的现象完全一致。

`AutoIoSeverHandle` 当前在 `GATT.c` 中声明为 `static`，所以 `Bluetooch.c` 无法
直接识别该句柄。修复时应由 GATT 模块注册控制句柄，或者把订阅状态管理改为
通用的句柄状态表，不建议仅靠增加未受控的跨模块全局变量解决。

## 已确认的问题

### 1. 上位机强制优先使用 Write Without Response

上位机检测到控制特征支持 `WriteWithoutResponse` 后，直接调用无响应写，
即使该特征同时支持普通 `Write` 也不会优先使用普通写。

日志中的 `AccessDenied` 是 Windows BLE API 的写入失败状态。因此该阶段不能
认为 ESP32 已经收到请求。

### 2. 上位机没有按实际 PDU 大小分片

`MODBUS-TX:[...]` ASCII 请求通常约 35 字节。默认 ATT MTU 为 23 时，单次
特征写入的有效载荷通常只有 20 字节。上位机当前没有读取并记录
`GattSession.MaxPduSize`，也没有按 `MaxPduSize - 3` 对请求连续分片。

ESP32 的 `BlueDataSubmit()` 支持跨多次 GATT 写入拼接 `MODBUS-TX:[...]`，
因此上位机可以安全地顺序分片发送。

### 3. ESP32 回复也依赖 MTU，发送失败目前不可见

ESP32 已调用 `ble_att_set_preferred_mtu(517)`，但这只是本端首选值，实际 MTU
仍取决于连接后的协商结果。

即使是读取版本号，包装后的 `MODBUS-RX:[...]` 文本也可能超过默认 20 字节
载荷。如果实际 MTU 没有增大，`ble_gatts_notify_custom()` 或
`ble_gatts_indicate_custom()` 可能返回失败。

当前 `SendMessage()` 中详细的发送失败日志被注释，因此设备端失败时，上位机
只表现为响应超时。

### 4. 上位机存在重复连接和重复订阅竞争

日志显示短时间内两次进入连接通道，并两次完成订阅。当前订阅入口没有
“正在连接”互斥状态，异步任务可能重复写入 CCCD、重复绑定 `ValueChanged`
事件，或在旧订阅尚未清理时建立新订阅。

## 固件链路核对

ESP32 固件当前处理链路为：

1. 控制特征 `AutoIoSeverCb()` 接收 Write/Write Without Response。
2. `BlueDataSubmit()` 按字符流识别并拼接 `MODBUS-TX:[...]`。
3. 完整帧进入 `BlueDataQueue`。
4. `ControlModbusProcess()` 校验 CRC 并处理站号 1，或转发站号 2/3。
5. 响应包装为 `MODBUS-RX:[...]`，通过同一控制特征 Notify/Indicate 返回。

该链路支持请求分片。当前最薄弱的环节是上位机写入策略，以及固件回复发送
失败时缺少可见日志。

## 修复优先级

1. ESP32 将控制特征加入 Notify/Indicate 订阅状态管理。
2. ESP32 在连接、断开时同步清除控制特征订阅状态。
3. ESP32 恢复静默拒绝原因和 Notify/Indicate 返回码日志。
4. 先验证读取站号 1 版本，确认控制回复实际进入 NimBLE 发送 API。
5. 上位机在同时支持两种写入方式时，MODBUS 事务优先使用普通 `Write`。
6. 获取 `GattSession.MaxPduSize`，按 `MaxPduSize - 3` 顺序分片发送。
7. 上位机增加连接/订阅互斥，避免重复绑定 `ValueChanged`。
8. 验证长响应，并根据实际 MTU 为 ESP32 响应增加分片。

## 验证要点

- ESP32 出现 `Bluetooth gateway text received`，证明至少有一个 GATT 写入到达。
- `BlueDataSubmit()` 收到完整结束符并成功入队。
- `ControlModbusProcess()` 返回成功。
- ESP32 Notify/Indicate API 返回 0。
- 上位机 `ValueChanged` 收到完整 `MODBUS-RX:[...]`。

如果第一项日志都没有，应继续检查上位机写入方式、分片和目标特征；如果前三项
成功但没有通知，应集中检查 MTU、CCCD 订阅状态以及 ESP32 的发送返回码。

## 11:52 后连接失败的进一步结论

最新上位机日志显示第一次仍能扫描到 `NUVELL-4026`，但在获取 GATT 服务时
返回 `Unreachable`；第二次扫描不到设备，并按旧 MAC 直连后再次返回
`Unreachable`。该问题发生在服务枚举阶段，尚未进入控制特征订阅逻辑。

对照上位机源码又确认了两个实现缺陷：

1. 手动连接和自动重连均调用无参数的 `GetGattServicesAsync()`，没有显式使用
   `BluetoothCacheMode.Uncached`。本次固件在 UUID 不变的情况下为控制特征
   新增 Notify/Indicate 和 CCCD，Windows 可能继续使用同一 MAC 对应的旧 GATT
   缓存。
2. 自动重连异常分支仅执行 `connectedDevice = null`，没有先对
   `BluetoothLEDevice` 调用 `Dispose()`。如果服务发现失败时底层连接已经建立，
   Windows 可能继续持有连接；ESP32 已停止广播，因此下一次扫描会找不到设备。

这两个问题共同给出一条与日志严格吻合的路径：

```text
扫描发现设备
  -> Windows 建立底层连接
  -> 使用旧缓存枚举已改变的 GATT 数据库
  -> GetGattServicesAsync 返回 Unreachable
  -> 异常分支未 Dispose，连接残留
  -> ESP32 保持已连接并停止广播
  -> 第二次扫描找不到设备
```

因此，“Windows GATT 缓存”仍需现场清缓存验证，但“失败连接没有释放”已经由
上位机源码确认，能够直接解释第二次扫描失败。

上位机应同时修改：

- 首次连接及固件升级后的服务枚举使用
  `GetGattServicesAsync(BluetoothCacheMode.Uncached)`。
- 特征枚举相应使用 `GetCharacteristicsAsync(BluetoothCacheMode.Uncached)`。
- 任何连接、服务发现或特征发现失败路径都取消事件、释放服务对象，并调用
  `connectedDevice.Dispose()` 后再置空。
- 下一轮重连前等待 Windows 完成断开，不能仅关闭再打开蓝牙适配器代替对象释放。

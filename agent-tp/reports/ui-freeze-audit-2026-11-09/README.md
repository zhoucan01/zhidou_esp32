日期：2026-11-09。分支 `ESP32_NEW_UI`，HEAD `37d7dd3`，以当前未提交工作区源码为检查对象。本次未修改固件、SDK、测试代码或构建配置，未构建/烧录 ESP32 固件；只阅读源码、运行现有显示启动主机测试、读取设备诊断并归档结论。

## 结论

**存在异常条件下长期无响应的路径，但没有发现 DMA 回调在正常路径上漏掉完成通知；本次也没有在设备上复现 UI 冻结。**

| --- | --- | --- |
| 取料到位等待 | 明确缺少超时、数据新鲜度检查及错误退出，满足异常条件时可持续锁住全部旋钮输入 | 正常模式 `MYLVGL_UI_VALIDATION_MODE=0` 的豆腐 Collect Pulp；当前默认 1 的 UI 入口绕过实际取料 |

## 1. 优先处理：豆腐取料后输入可能长期锁定

位置：[取料任务](../../../function/UI/Tofu/ui_tofu_ready.c:18)、[UI 取料入口](../../../components/myLvgl/myLvgl.c:573)。

正常模式下，点击 Collect Pulp 创建后台任务，依次发送抬升上行、等待 `riseHighPos==1`、停止抬升、等待 300 ms、压制上行、等待 `pressHighPos==1`、停止压制、播放音乐、恢复电流档位，最后才清除 `collecting`。

确认的缺口：

1. [抬升等待](../../../function/UI/Tofu/ui_tofu_ready.c:23)与[压制等待](../../../function/UI/Tofu/ui_tofu_ready.c:30)均只有每 100 ms 让出 CPU，没有截止时间、取消或故障分支。任一信号始终为 0，任务就无法执行到清除 `collecting` 的位置。
2. 等待使用的 `getSensorData()` 直接读取 `sensorState[]`，没有使用已有的 `DataCenterGetSensorSnapshot()` 新鲜度检查。站2通信中断后，该数组会保留之前的状态；旧 0 可以导致一直等，旧 1 则可能使步骤提前通过。是否真实到位不能只依据陈旧缓存。
3. [电机命令包装](../../../task/DataCenter/DataCenter.c:400)及速度包装调用 `command_queue_push()` 后忽略返回值，电机 API 又是 void。队列满时会警告并返回 false，但取料任务无法知道命令未入队，也没有通过读取目标/反馈确认动作开始，仍然进入到位等待。这是可由软件触发的条件，不只取决于机械或开关损坏。
4. 取料时，[旋转](../../../components/myLvgl/myLvgl.c:428)、[短按](../../../components/myLvgl/myLvgl.c:470)、[长按](../../../components/myLvgl/myLvgl.c:633)入口均直接返回；[页面收尾](../../../components/myLvgl/myLvgl.c:220)也只在 `collecting` 清除后才回首页。因此异常时用户会一直停在豆腐完成页，所有旋钮操作都没有效果。

这里通常是**业务等待加输入锁定**，不是 LVGL 渲染线程本身停止；通信和其他任务仍可能运行。任务创建失败的分支已经清除 `collecting`，可重试，不是本项问题。

当前 `myLvgl.h` 的默认值是 1，正常 UI 按下 Collect Pulp 只回首页；上述真实取料问题不会从当前默认演示入口触发。不能因此认为正常模式已具备超时保护。

现有正常模式主机测试模拟到位信号约 200 ms 后成功，并覆盖任务创建失败重试、取料期间输入锁定和正常收尾；**未覆盖“永远不到位”“命令队列满”“通信数据过期”的退出恢复**。

## 2. DMA 回调：正常路径没有发现漏释放

位置：[回调注册](../../../components/myLvgl/lv_port_disp.c:145)、[回调实现](../../../components/myLvgl/lv_port_disp.c:216)。

已核对：

- 驱动和用户上下文使用静态对象，不是返回后失效的栈上局部变量。
- `esp_lcd_panel_io_register_event_callbacks()` 的结果经过 `ESP_ERROR_CHECK`，注册失败不会被静默忽略。
- 回调内只有首帧/帧耗时统计受 `lv_disp_flush_is_last()` 条件控制，`lv_disp_flush_ready()` 位于条件外，**每一条带完成都会调用**。
- 最后一块标志在调用 flush_ready 前读取，避免该函数清除标志后统计失效。
- 回调没有申请堆内存、调用 LEDC 或打印日志；背光交给 UI 线程处理。帧统计和帧时间锁未发现互相反向持锁的链路。
- 驱动返回明确错误时，`disp_flush()` 先释放 flushing 标志，再通过错误检查进入异常处理，属于可能 abort/重启的路径，不能与“已经返回成功、后来没有完成回调”混为一谈。
- 当前代码中未找到第二处对同一 IO 替换完成回调的活动调用。回调返回 false 本身不是漏释放：它表示本回调没有请求额外调度，不影响显式调用 flush_ready。

本次重跑现有 `test_display_startup.py` 通过，覆盖 8 个 60 行条带分别释放、仅最后一块完成才计帧/亮屏、错误路径及启动握手。**测试使用同步模拟的完成事件，不证明实际中断永不丢失。**

## 3. 显示链：不仅 LVGL，I80 驱动内也有无超时等待

[LVGL 等待](../../../components/lvgl/src/core/lv_refr.c:1279)在当前双缓冲、分条刷新配置下会实际执行，不是未启用的死代码。`flushing` 是 volatile，不能简单归因于编译器没有重新读取这个变量。

调用关系为：

```text
UI 线程 → lv_task_handler → LVGL 分条刷新
       → esp_lcd_panel_draw_bitmap
       → ST7796 设置地址窗口并提交像素
       → I80 传输完成中断 → 应用回调 → lv_disp_flush_ready
```

若已经提交的颜色传输没有完成回调，LVGL 下一次等待 `flushing==0` 时没有超时；工程没有设置 `wait_cb` 让出 CPU或执行异常检测，也没有独立的显示恢复状态机。UI 的时基、旋钮分发和刷新位于同一线程，陷入该循环后都无法继续。

继续阅读构建记录实际指向的本机 ESP-IDF 5.3.1 源码，确认还有两类等待：

- `C:/esp/v5.3.1/esp-idf/components/esp_lcd/i80/esp_lcd_panel_io_i80.c:434` 等位置，回收传输描述符使用 `xQueueReceive(..., portMAX_DELAY)`；颜色提交也使用无限队列等待。
- 同文件第 466 行等位置，设置地址窗口参数时轮询 `LCD_LL_EVENT_TRANS_DONE`，没有截止时间。ST7796 每次 draw_bitmap 先发 CASET/RASET，所以即使尚未提交新的颜色传输，也可能停在底层参数传输中。

因此，只给 LVGL 的一个 while 加超时，不能覆盖底层函数内部阻塞。正常完成链路目前是正确的，但在外设/中断状态异常不再推进时没有恢复保障。本次没有制造中断丢失，也没有证据表明当前设备正在发生该异常；不能直接把面板排线问题等同于本机 DMA 中断必然丢失。

当前任务看门狗开启、超时 5 秒，但 `CONFIG_ESP_TASK_WDT_PANIC` 未启用。因此不能依赖任务看门狗必然自动重启恢复；中断看门狗覆盖的是另一类中断长期受阻情况。

## 4. 其他仍可能呈现“卡住”的位置

### 4.1 内存断言

`CONFIG_LV_USE_ASSERT_MALLOC=y`，默认 [LV_ASSERT_HANDLER](../../../components/lvgl/src/lv_conf_internal.h:741) 为 `while(1)`，同时 LVGL 日志关闭。图层上下文、Label 文字或临时缓冲申请失败，可在 UI 线程中断言后不再推进。

Custom Milk 原先像素缓冲 NULL 后清零的问题仍保持修复：该处先判空返回，上层会跳过相应图层；不能把它与图层上下文分配时的断言当成同一个失败路径。图片解压缓冲也有 NULL 返回处理，不能认为每一笔 PSRAM 申请失败都必然冻结。

既有正常场景池峰值 34,104 B / 131,072 B 没有接近上限，但不覆盖所有碎片/损坏/并发状态；本次实机 FC04 也读不到 LVGL 私有池 largest 或 min-free。

### 4.2 启动握手

[UI 启动分支](../../../components/myLvgl/myLvgl.c:708)等待首帧完成没有截止时间，然后 `ulTaskNotifyTake(..., portMAX_DELAY)` 等应用初始化完成通知。主入口的 1500 ms 限制只限制主入口自身等待首帧的时长，**不会让已经卡住的 UI 启动分支自动退出**。

正常通知在后台任务初始化结束后送达，提前到达的任务通知可以保留，未发现正常顺序丢通知的问题；但初始化不再推进时，没有 UI 侧失败页或超时退出。

### 4.3 停止页等待

正常模式下，豆腐、植物奶和清洗依靠实际任务状态退出 Stopping。任务没有结束时，页面可能一直等待且输入被禁止；页面没有另设最大停止时长。它与刷新线程卡住不同，应先核对实际任务及停止命令执行情况。演示模式则使用约 2 秒的模拟停止时间，不能验证真实任务异常退出。

未做：显示中断丢失、驱动外设卡死、永远不到位、命令队列满、陈旧传感器的实机故障注入；未做长期 UI 切页与无线并发验证。本次不新增故障注入程序，不调整代码或设备设置。

建议后续实施顺序（本次均未实施）：

1. 正常模式的取料应具有分阶段超时、传感器快照有效性、命令提交/反馈检查和统一故障收尾；不能只清 UI 锁而忽略执行器仍可能运行。
2. 显示侧增加独立于 UI 线程的进度诊断，再设计驱动/DMA停止和重新初始化后的恢复；不要在 DMA 尚未确认停止时直接强制 flush_ready，否则可能复用仍在传输的缓冲区。
3. 建立可观测的内存断言/错误记录和有界的启动、停止等待，再按异常类别决定恢复或故障提示；不要简单关闭断言。
